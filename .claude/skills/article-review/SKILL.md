# 技術記事をレビューする

azukiazusa.dev の読者と編集者の立場から、記事が正確かつ効率よく読め、このブログの構成・文体を再現しているか確認する。

## 対象を特定する

引数がスラッグなら `contents/blogPost/<slug>.md` を対象にする。Markdown ファイル、貼り付けた本文、または明確に特定された記事も受け付ける。複数候補があり推定できない場合だけ確認する。

既定ではレビューだけを行い、ファイルを変更しない。編集はユーザーが明示的に依頼した場合だけ行う。

記事全体と次のガイドを読む。

- [`../../../contents/BLOG_WRITING_GUIDE.md`](../../../contents/BLOG_WRITING_GUIDE.md)
- [`../../../contents/writing-style.md`](../../../contents/writing-style.md)
- [`references/editorial-checklist.md`](references/editorial-checklist.md)

同じ記事タイプの既存記事を 2〜3 本選び、表現をコピーせず、導入、見出しの進行、説明のリズム、コードと媒体の扱い、まとめ方を比較する。

## 自動校正を補助として使う

対象がリポジトリ内のファイルで textlint が利用できる場合は、リポジトリルートから実行する。

```bash
./contents/node_modules/.bin/textlint \
  --config ./contents/.textlintrc.json \
  ./contents/blogPost/<slug>.md
```

`error` と `warning` を区別する。弱い表現や冗長表現などの warning は、筆者の意図や house style と整合する場合は無理に修正しない。同じ規則による大量の指摘は 1 件へまとめ、代表行と記事全体へ適用する修正規則を示す。textlint が利用できない場合は手動レビューを続け、実行したと主張しない。

## 記事をレビューする

チェックリストに従い、次を確認する。

- `title` と `about` が本文の対象と到達点を正確に表しているか
- 導入で課題、対象読者、範囲、到達点が分かるか
- 前提から実用例へ自然に進み、見出しが読者の疑問や作業順に並ぶか
- コードや媒体の前後に目的、重要箇所、観測結果の説明があるか
- 見た目や操作が重要なのに媒体も具体的な `TODO(media)` コメントも欠けていないか
- 公開されない内部検証成果物のパス、起動コマンド、リポジトリ上の場所へ言及していないか
- 文法、誤字脱字、用語、句読点、日本語と英数字のスペースが一貫しているか
- `まとめ` が本文の具体的な結論を再掲し、`参考` に一次情報があるか

文体上の好みだけを誤りにしない。ただし、ガイドに明記された house style との差は指摘する。技術的な真偽を確認したとは主張せず、読者への影響を説明したうえで `tech-review` の検証事項として分ける。

## 指摘を報告する

重要度順、同じ重要度では行番号順に並べる。

- `P0`: 記事として利用できない、または重大に誤解させる
- `P1`: 公開前に直すべき構造・言語上の問題
- `P2`: 明確さや読者体験を有意に改善する問題
- `P3`: 任意の改善

```text
[P1] 短い指摘タイトル
Location: contents/blogPost/example.md:42
Impact: 読者が理解できないこと、または誤解すること
Suggestion: 具体的な置換、移動、削除、追記
```

同じ原因の指摘はまとめ、場所を特定するために必要な範囲だけ引用する。指摘がなければその旨と、確認できなかった範囲を伝える。求められない限り、良い点のセクションは作らない。

## 依頼された修正を適用する

ユーザーが編集を依頼した場合だけ、意味と筆者の声を保って修正する。論旨、技術的主張、範囲、意見を黙って変えない。媒体が必要だが用意できない場合は、正確な位置へ次のコメントを置き、前後に観察点と解釈を書く。

```markdown
<!-- TODO(media): <画像|動画|インタラクティブデモ>で<具体的な状態または操作>を示す。読者が確認する点: <具体的な結果>。代替テキスト・キャプション: <説明>。 -->
```
