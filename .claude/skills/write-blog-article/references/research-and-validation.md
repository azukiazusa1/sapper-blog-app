# 一次情報の調査とサンプル検証

## 調査

新しい API、Web 標準、ライブラリの新機能では次の順に調べる。

1. 現在の仕様書、Explainer、公式 API ドキュメント
2. 仕様策定の Issue、Pull Request、メーリングリスト、会議録
3. 実装リポジトリ、Intent to Prototype/Ship、公式リリースノート
4. 他ベンダーの Standards Position、互換性情報、未解決 Issue
5. 公式テスト、Web Platform Tests、公式サンプル

MDN や第三者の記事は発見と理解の補助に使えるが、中心的な主張の唯一の根拠にしない。検索結果の要約を根拠にせず、リンク先を読む。

仕様策定の議論から次を抽出する。

- 解決しようとしていた具体的な問題
- 検討された代替案
- 現在の構文・名前・責務になった理由
- 意図的に対象外とされた機能
- 合意していない点と今後変わり得る点

設計理由が資料に明記されていない場合は推測しない。議論の日付と現在の仕様を混同しない。

## 記事の主張と検証を対応させる

サンプルを作る前に、検証する中心的な正常系を1つに絞る。必要な場合だけ、追加の主張と観測方法を対応させる。

| 主張の例                         | 観測方法の例                       |
| -------------------------------- | ---------------------------------- |
| API が値を返す                   | 画面出力、コンソール、アサーション |
| DOM やアクセシビリティが変化する | DOM、Accessibility Tree、支援技術  |
| エラーが発生する                 | 例外の種類と発生条件               |
| フォールバックが機能する         | 未対応条件を再現した画面・ログ     |
| 型が保証される                   | typecheck、型テスト                |

## サンプルを作る

- `examples/<slug>/` に完全なファイル一式を置く
- 新しい API を呼び出し、中心的な正常系が動くことだけを確認できる最小例にする
- 説明文、手順、テスト結果一覧をサンプル画面に表示しない。説明は記事本文に置く
- デモ専用 UI、独自のテストハーネス、動作確認に不要なスタイルを追加しない
- import、依存関係、環境変数、起動コマンドを省略しない
- 自動テストや失敗条件は、記事の中心的な主張を証明するために不可欠な場合だけ追加する
- 自動化できない UI や実験的 API は、再現可能な実機確認手順を残す
- 人間が再実行できるコマンドを完了報告に記載する
- サンプルを自動削除・自動ステージ・自動コミットしない

## 実環境で検証する

1. 対象 API を実装しているブラウザまたはランタイムとバージョンを確認する
2. サンプルを起動する
3. 合意した成功条件を観測する
4. 重要な制約・エラー条件を確認する
5. 実行コマンド、検証日、環境、結果を記録する
6. 記事のコードと検証済みコードが一致することを確認する

対象環境がなければ、安全な代替環境、Technology Preview、Nightly、機能フラグを調べる。インストールや設定変更には承認を得るが、同じ対象・操作について承認済みなら再確認しない。検証できない場合は記事を「検証待ち」とし、成功したように書かない。資料調査、観測に依存しない説明、静的レビューは進め、完成扱いにする前に未完了の検証を解消する。

## 技術レビューで確認する

- 仕様上の規範的要件と実装固有の挙動を区別したか
- 検証した環境を他環境へ一般化していないか
- 策定途中の議論を現在の結論として扱っていないか
- サンプルにセキュリティ、アクセシビリティ、互換性上の問題がないか
- コード、本文、クイズの説明が同じ挙動を示しているか
