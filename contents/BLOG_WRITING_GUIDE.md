この文書は、`contents/blogPost/` にある既存の日本語記事から共通パターンを抽出し、新しい記事を書くときに再利用できる形にまとめたものです。

- 調査日: 2026 年 8 月 15 日

- 除外: `contents/blogPost/en/` の英訳記事、`published: false` の下書き 41 件、`index.html`
- 現在のスタイルを把握するため、2025 年以降の記事 163 件を重点的に確認

数値は Markdown の機械集計、構成と文体の特徴は新旧・分野の異なる記事を目視して確認した結果です。過去の記事には現在と異なる書式が含まれるため、新規記事では「2025 年以降」の傾向を優先します。

## 結論

このブログの記事は、技術を網羅的に説明するリファレンスというよりも、**読者が抱える具体的な問題を起点に、必要な概念を説明し、動く例や調査結果で確かめる実践的な解説記事**として書かれています。

もっとも再現性の高い基本構成は次のとおりです。

1. 問題・背景・読者が得られることを導入で示す
2. 前提となる概念や、従来手法の課題を説明する
3. 小さなコード例から実際の利用例へ進む
4. 制約、未対応環境、代替手段を明記する
5. 「まとめ」で要点を箇条書きにする
6. 「参考」に一次情報へのリンクを並べる

## 共通する記事構成

### 1. frontmatter

すべての公開記事は、本文とは別にタイトル、概要、日時、タグ、サムネイルなどを持ちます。2025 年以降は理解度チェックも共通要素です。

- `title`: 技術名と記事で行うことを組み合わせる
- `slug`: 英小文字の kebab-case
- `about`: 背景、対象技術、記事で扱う内容を 2〜3 文で要約する
- `createdAt` / `updatedAt`: タイムゾーンを含める
- `tags`: 広い分類と固有技術を 2 個程度指定する
- `thumbnail.title`: 画像の内容がわかる代替テキストにする
- `selfAssessment`: 記事の主要な学習事項を確認する 4 択問題を置く

`about` は検索結果や記事一覧だけで内容が判断できるよう、結論を隠さず具体的に書きます。

### 2. 導入

導入では「なぜ読む必要があるか」を先に示します。単に「X について説明します」から始めるのではなく、次の順序がよく使われています。

1. 読者が遭遇する状況や、従来手法の課題
2. 対象技術がその課題にどう関係するか
3. この記事で扱う範囲と到達点
4. 必要なら動作確認環境や重要な結論

典型的な到達点の示し方は「この記事では、〜を紹介します」「この記事では、〜を実装します」です。

実験的な API やバージョン依存の機能は、導入の先頭か概念説明の直後に警告を置きます。日付、対応バージョン、仕様の安定度、フォールバックを具体的に書くのが特徴です。

### 3. 本文

見出しは読者の作業または疑問に沿って並びます。技術の内部構造だけで分割せず、読者が次に何をするのかわかる見出しにします。

よくある流れは次のとおりです。

- 対象技術・API の定義
- 従来の実装や解決したい問題
- インストール、プロジェクト作成、設定
- 最小の利用例
- 機能を追加した実践例
- 実行結果、画面、ログによる確認
- 制約、エラー、アクセシビリティ、互換性

説明は「主張→コードや図→観察結果→意味」の単位で進みます。コードだけを連続させず、コードの前に目的、後に重要な行や実行結果を説明します。

### 4. まとめ

本文で得た結論を、単独で読んでも意味が通る箇条書きにします。近年の記事では、各項目は短い体言止めよりも「何ができる」「何に注意する」のような具体的な命題です。本文にない新情報は追加しません。

### 5. 参考

仕様、公式ドキュメント、公式ブログ、実装リポジトリ、Issue や Pull Request などを箇条書きにします。本文中にも根拠となる箇所から直接リンクし、末尾の「参考」は調査元の一覧として使います。

## 記事タイプ別の型

### 新しい API・機能の紹介

例: [`fetch-text-stream.md`](./blogPost/fetch-text-stream.md)、[`aria-actions-attribute.md`](./blogPost/aria-actions-attribute.md)

1. 対応状況の警告
2. 現在の課題または従来のコード
3. 新機能の位置付け
4. 最小の使用例または差分
5. 仕様上の細かな挙動
6. 実際に動かす例
7. 制約とフォールバック
8. まとめ・参考

### ハンズオン・実装チュートリアル

例: [`instrument-hono-logs-with-opentelemetry.md`](./blogPost/instrument-hono-logs-with-opentelemetry.md)、[`yaml-file-defined-ai-agent-cagent.md`](./blogPost/yaml-file-defined-ai-agent-cagent.md)

1. 技術の概要と完成形
2. 必要なら構成図
3. プロジェクト作成・インストール
4. ファイル単位の段階的な実装
5. 起動・操作コマンド
6. 期待するログや画面
7. 応用機能または運用上の注意
8. まとめ・参考

### 調査・比較記事

例: [`accessible-streaming-chat-ui.md`](./blogPost/accessible-streaming-chat-ui.md)

1. 調査対象となる具体的な問題
2. 調査範囲と検証環境
3. 判断に必要な標準・基礎概念
4. サービスやライブラリごとの観察
5. 共通点と相違点
6. 調査結果を反映したサンプル
7. 実機での検証結果
8. まとめ・参考

### 意見・経験記事

例: [`recent-ai-coding-development-process-centered-on-design.md`](./blogPost/recent-ai-coding-development-process-centered-on-design.md)

1. 現在の立場や経験の変化
2. テーマごとの実践と理由
3. 利点だけでなく限界や反論
4. 今後変わり得る点
5. まとめ

意見記事では一人称を使いますが、一般的な技術解説では主観を前面に出さず、コード、仕様、実行結果を根拠にします。

## 文章のスタイル

### 基本文体

- 「です・ます」の敬体で統一する
- 一文一義を意識し、原因、操作、結果を詰め込みすぎない
- 最初に結論や目的を示し、その後で理由を説明する
- 読者への操作案内には「〜してみましょう」「〜してください」を使う
- 推測は「〜と考えられます」「〜可能性があります」として、確認済みの事実と分ける
- 強い断定をする場合は、仕様、公式文書、実行結果のいずれかを根拠にする

常体の「〜である」「〜だ」はほとんど使われません。ただし、箇条書きや図中の短いラベルでは文末を省略できます。

### 用語と表記

- API、属性、関数、変数、ファイル名、コマンドはインラインコードにする
- 技術名は公式表記を使う。例: JavaScript、TypeScript、Node.js、OpenTelemetry
- 日本語と英数字の間に半角スペースを入れる。例: `AI エージェント`、`3 つの方法`
- 数字は原則として半角を使う
- 初出の略語は説明する。例: `OTLP（OpenTelemetry Protocol）`
- 同じ概念に複数の訳語を使わない
- 機能名の初出には公式ページへのリンクを付ける

### 説明の運び方

次の表現が記事全体のリズムを作っています。

- 導入: 「〜という問題があります」「この記事では〜を紹介します」
- 展開: 「まずは〜を確認しましょう」「続いて〜を実装します」
- コード導入: 「以下のコードでは〜」「`foo` ファイルを作成します」
- 結果: 「以下のように表示されれば成功です」「〜ことが確認できます」
- 注意: 「〜という点に注意してください」「実際のプロダクトでは〜が必要です」
- 対比: 「一方」「しかし」「つまり」を使い、違いや結論を明示する

「〜できます」は多用されやすいため、能力、仕様、実行結果のどれを表しているかが曖昧にならないようにします。

## コード・画像・注記の扱い

### コード

- コピーして試せる単位を優先する
- 必要な import、インストール、起動コマンドを省略しない
- 長い完成形を最初に置かず、最小例から段階的に追加する
- ファイルを作る場合は、コードフェンスの言語指定に `ts:src/example.ts` のようにパスを付ける
- 変更点の比較には `diff` を使う
- コメントは自明な動作ではなく、選択理由や注意点を書く
- コードの直後に、重要な行と期待する結果を説明する
- バージョンに依存する場合はインストール例でバージョンを固定する

### 画像・動画

- UI、開発者ツール、ログなど、文章だけでは確認しづらい結果に使う
- 画像の前に「何を見るのか」、後に「何が確認できたのか」を書く
- 操作や時間変化が重要な場合は動画、読者が触れる価値がある場合は CodePen などの埋め込みを使う

### 注記

- `info`: 補足知識や仕様上の詳細
- `note`: 本筋を止めるほどではない実装上の注意
- `warning`: 互換性、破壊的変更、本番利用上のリスク
- `!>`: 導入直後に強く示す短い警告

注記の中に重要な手順を隠さないようにします。記事を完了するために必須の操作は本文に置きます。

## コピーして使う記事テンプレート

`id`、日時、サムネイルは実際の記事作成フローに合わせて置き換えます。

````markdown
---
id: <記事 ID>
title: "<技術名> で <できること・解決すること>"
slug: "<kebab-case-slug>"
about: "<背景・課題>。<対象技術の要点>。この記事では <扱う内容と到達点>。"
createdAt: "YYYY-MM-DDTHH:mm+09:00"
updatedAt: "YYYY-MM-DDTHH:mm+09:00"
tags: ["<広い分類>", "<固有技術>"]
thumbnail:
  url: "<画像 URL>"
  title: "<画像の内容>"
audio: null
selfAssessment:
  quizzes:
    - question: "<記事の中心的な理解を確認する質問>"
      answers:
        - text: "<正答>"
          correct: true
          explanation: "<正しい理由>"
        - text: "<誤答>"
          correct: false
          explanation: "<誤っている理由>"
        - text: "<誤答>"
          correct: false
          explanation: "<誤っている理由>"
        - text: "<誤答>"
          correct: false
          explanation: "<誤っている理由>"

---
````

## 公開前チェックリスト

### 構成

- [ ] 導入だけで対象読者、課題、到達点がわかる
- [ ] 見出しの順序が読者の疑問や作業手順に沿っている
- [ ] 背景説明が実装より長くなりすぎていない
- [ ] 各節が次の節を読む理由を作っている
- [ ] 「まとめ」が本文の結論を過不足なく再掲している
- [ ] 「参考」に一次情報が含まれている

### 技術的な信頼性

- [ ] コードを新しい環境でコピーして実行できる
- [ ] import、依存関係、環境変数、起動手順を省略していない
- [ ] 対象バージョンと検証環境を記録した
- [ ] 実験的な仕様は記事執筆時点の日付と対応状況を明記した
- [ ] 公式仕様と実際の挙動、自分の推測を区別した
- [ ] セキュリティ、アクセシビリティ、互換性の注意点を確認した

### 文章

- [ ] 「です・ます」で統一した
- [ ] 同じ用語を同じ表記で使った
- [ ] 一文に複数の論点を詰め込んでいない
- [ ] 「これ」「それ」が何を指すか明確である
- [ ] コード、画像、リンクの前後に説明がある
- [ ] `about` が本文を読まなくても内容を判断できる要約になっている

### 学習体験

- [ ] `selfAssessment` は暗記ではなく、記事の中心概念を確認している
- [ ] 選択肢は 4 つで、正答が 1 つだけである
- [ ] 誤答は明らかな冗談ではなく、読者が混同しやすい内容である
- [ ] 正答・誤答の理由を `explanation` で説明している

## 運用上の注意

このガイドは既存記事の傾向を記録したものであり、すべての記事を同じ長さや見出し数に揃えるための規則ではありません。短い API 紹介なら数節で終えてよく、意見記事に無理にコードを追加する必要もありません。一貫させるべきなのは分量ではなく、**課題と到達点が明確であること、具体例で確かめること、制約を隠さないこと、読後に要点を持ち帰れること**です。
